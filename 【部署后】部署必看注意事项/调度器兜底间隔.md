# 调度器兜底巡检间隔（poll_interval_ms）

**本文件只管部署后**：这是实例配置文件 `compute.toml` 里的一条设置，重新初始化（init）会重新生成该文件，这条设置会丢——每次重装后必须按本文补回。

## 这条设置管什么

调度器平时是**事件驱动**的：任务一创建立即被唤醒，不靠轮询。`poll_interval_ms` 只是一层兜底——万一唤醒通知在程序内部丢失，最多隔这么久强制醒一次巡检，防止任务永远没人处理。

## 为什么必须改（上游默认值的坑）

上游默认 **100 毫秒**。后果：即使整个系统完全空载、数据库里没有任何待办，调度器每秒也要醒 10 次，每次做一整轮四个数据库的汇总查询 + 指标采集——**空载常态约 5% 单核 CPU，永不归零**。

社区同类项目的实践（Zeebe #14187、Rapid-MLX #265、vLLM-MLX #552）都确认：事件驱动架构下放宽这个间隔没有响应速度代价。

## 怎么设置

`compute.toml`（数据目录里 `instances/default/compute.toml`）加一段：

```toml
[scheduler]
# 兜底巡检间隔：上游默认 100ms 导致空载每秒 10 轮全量 SQL 汇总（常态 ~5% 单核）。
# 放宽到 1 秒；有任务时仍是事件驱动立即唤醒，不受影响。上游修复默认值后可移除。
poll_interval_ms = 1000
```

改完 `docker compose restart open-compute` 生效。

## 实测对比（2026-10-22，同一台机）

| 配置 | ocd 空载实际 CPU（60 秒精确采样） | 说明 |
|---|---|---|
| 默认 100ms | **5.37%** 单核 | 每秒 10 轮全量 SQL 汇总 |
| 1000ms | **2.00%** 单核 | 每秒 1 轮，降 63%；任务创建后立即被处理（实测 1 秒内进 running，事件驱动不受影响） |

想再压低可放宽到 5000（约 0.4~0.5%），代价只是兜底巡检最迟 5 秒发现一次通知丢失——事件路径正常时无感。

## 验证方法

```bash
# 两次采样 ocd 进程的 CPU 时间（utime+stime），间隔 60 秒，算单核百分比
docker exec open-compute sh -c 'cat /proc/1/stat' | awk '{print $14, $15}'
```
